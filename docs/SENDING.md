# 两种发送方式

| | 立即补充当前任务 | 本轮完成后发送 |
| --- | --- | --- |
| 操作 | 用户点击后，立即尝试提交原生草稿 | 用户启用后，等待本轮结束证据 |
| 本轮仍在运行 | 允许，原生发送按钮必须可用 | 等待，不提交 |
| 结束约定 | 不需要 | 必须提前设置 |
| 附件 | 使用原生输入框里已上传的附件 | 同样保留原生附件 |
| 当前任务是否接纳新要求 | 由网页当前行为和设置决定 | 仅在严格条件满足后提交下一条 |
| 结果不明 | 保留锁定，不重试 | 保留锁定，不重试 |

## 立即补充不等于强制 Steer

扩展不调用私有 ChatGPT 接口，也不切换网页未识别的发送设置。立即补充只是现在提交原生输入框的内容。网页可能把它作为当前任务的补充，也可能加入原生队列；并不保证马上被模型采纳。

官方说明区分 Steer（加入当前运行）与 Queue（留给下一轮）。不同端的选项和可用性可能不同，不能从按钮颜色推断网页一定采用哪种行为。

参考：https://learn.chatgpt.com/docs/prompting

## 共享保护

两种方式都检查唯一输入框、发送按钮、附件上传、页面警告、对话和草稿变化，并使用同一份发送记录及聊天回执核验。停止按钮即使带有过期的发送标签，也不会被当作发送按钮点击。

立即提交后，若新消息只进入网页原生队列而没有出现在聊天记录，当前版本会显示“提交尚未在聊天记录确认”，保留待核验锁。它不会根据输入框变空就声称模型已收到，也不会自行重试。检查聊天记录／原生队列后，可在设置中手动解除锁定。

## 完成后模式

只有完成后模式和扩展自己的文字队列需要随机结束约定。详见 [完成检测](COMPLETION.md)。立即补充不自动启用延后发送，也不消费本轮结束口令。
