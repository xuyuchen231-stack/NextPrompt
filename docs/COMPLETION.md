# 发送箭头可用，不等于本轮完成

NextPrompt 不读取发送箭头的颜色，也不会仅凭按钮从禁用变为可用就发送下一条。

## 三种状态需要区分

| 状态 | 能说明什么 | 能否据此自动发送下一条 |
| --- | --- | --- |
| 输入框允许发送 | 页面接受提交操作 | 单独不可以 |
| 正在生成一段文字／展示进度 | 当前消息或任务仍在推进 | 不可以 |
| 整轮任务结束 | 当前轮次已停止推进，可以开始下一轮 | 本项目希望识别的目标，但只能通过 DOM 推断 |

有些界面可能在任务进行中就允许用户提交内容。因此“发送按钮可用”不是任务生命周期的可靠边界；不能从蓝色箭头判断工具调用、代码修改、测试或后台工作都已结束。

## 当前代码实际依据

`adapter.js` 读取：

- 已知停止生成按钮、流式输出或思考标记是否可见。
- 最新用户消息之后，最后一个助手消息所在轮次是否存在已支持的复制／反馈操作按钮。
- 页面警告、附件进度和发送按钮可用状态。

`engine.js` 再检查：对话、用户消息数量、草稿和附件是否符合启用时的快照；在上述条件满足后，默认等待 12 秒稳定期。发送控制器点击前再次检查状态，发送后核验新用户消息。

**稳定期不代表任务必然完成。** 它只减少短暂 DOM 变化造成的误判，不能证明后台没有任务。

## 当前实现的可靠性边界

复制／反馈按钮是启发式标记，不是官方的 turn-completed 事件。如果 Work 的中途进度消息也带复制按钮，而且运行状态没有被适配器识别，当前逻辑仍可能误判。相反，页面不显示预期按钮时，也可能一直等待。

当前版本未在真实登录 Work 页面完成验收，不能宣称准确识别了所有 Work 任务结束信号。单元测试能够证明判断逻辑不会仅因发送按钮可用而放行，不能证明真实页面快照总能正确表达任务状态。

## 后续适配应验证什么

需要用真实长任务观察：中途进度、工具执行、等待用户确认、最终交付这几种状态的可见结构。优先找明确且稳定的整轮运行／完成信号，再增加夹具和测试；无法区分时应暂停自动发送。不要使用固定坐标、按钮颜色或“文字静止一段时间”替代完整判断。

发送自动化与 API 工作流是不同路径。未来若使用有明确生命周期事件的 API，可直接使用该接口的状态，但该状态不会自动代表当前 ChatGPT 网页对话的任务状态。
